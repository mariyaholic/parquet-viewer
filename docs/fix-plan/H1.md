## Root cause
The text layer feeds LF-only strings to a control that requires `\r\n`. The review's problem statement was "make text pretty"; the missing step is a newline-encoding boundary between Rust strings and the Win32 EDIT control.

## Fix (minimal)
- Touch only `crates/windows/src/handler.rs`:
  - Add a private helper `fn to_crlf(text: &str) -> String` that inserts `\r` before every `\n` not already preceded by `\r` (idempotent: leaves existing `\r\n` alone, never produces `\r\r\n`).
  - Apply it inside `set_window_text` (`handler.rs:361-366`) before `ffi::wide`. All three call sites funnel through it (rendered text, `error_text`, About/message paths), so nothing else changes.
- Do **not** change `ffi::wide` — it is also used for paths and registry keys where conversion would corrupt values (this is the alternative we reject).
- Rejected alternative: `EM_SETEXTENDEDSTYLE(ES_EX_ALLOWEOL_ALL)` after edit creation — needs Windows 10 1809+ (README messaging for 07b targets older bases) and additional `ffi.rs` plumbing; CRLF conversion is universal and smaller.

## Acceptance test
- Unit (no Windows needed): `crates/windows/src/handler.rs` gains `#[cfg(test)] mod tests` with `lf_text_is_converted_to_crlf`: assert `to_crlf("a\nb\n\nend") == "a\r\nb\r\n\r\n" + "end"`, `to_crlf("x\r\ny") == "x\r\ny"`, and `to_crlf("solo")` unchanged. Before the fix the helper does not exist, so the test cannot pass; after, green.
(Wait — the assertion above is for `"a\nb\n\nend"` → keep exactly `"a\r\nb\r\n\r\nend"`; either way the point is: every bare `\n` becomes `\r\n`, existing `\r\n` untouched.)
