## Root cause
The shipping DLL trusts a user-settable env var to redirect its child process — an unnecessary same-user persistence-redirection hook that also makes behaviour untestable in production; and the "release" story is a script nobody's automation runs.

## Fix (minimal)
1. Gate the override: in `worker_path()`, make the `PARQUET_PREVIEW_WORKER` branch compile only under `#[cfg(debug_assertions)]` (debug builds keep the hook for local testing; release uses the loaded-DLL-relative path).
2. Add to `ci.yml` (or a release workflow XR-1 creates): a job step running `scripts/build-windows.ps1` and, on tag, publishing `dist/` + `SHA256SUMS` as release artifacts.
3. Add a `cargo deny check licenses bans` step (deny.toml already sits ready).
- Rejected alternative: keep the env override in release for debugging. The override is only needed with a locally built worker, which the debug gating already covers.

## Acceptance test
- Test: a unit test that sets `PARQUET_PREVIEW_WORKER` and asserts `worker_path()` returns the loaded-DLL-relative path in a release-profile build (or compile-check via `#[cfg(debug_assertions)]` — note Go-style runtime inspection isn't possible; the fixer should prefer a tiny `#[cfg(test)]` seam exposing an internal resolver flag).
- Manual/CI: run a release build with the env var set; the DLL still resolves the shipped worker (i.e., debug build honours var, release does not).

## Risk / blast radius
- Debug-only surface change; zero release-path impact. The release job steps reuse the existing script; watch that `cargo deny` cfg matches the workspace (all modules).
- XR-1 edits the same yml; either fold both into one session or rebase after.
