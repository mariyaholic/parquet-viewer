# parquet-viewer L3 — `TerminateProcess` by PID races PID recycling because the child's last handle is dropped before the PID slot is cleared

- Severity: low
- Pinned SHA verified: `e815e646e6d261291417730ac79345da81e7f6f9`
- Status: **CONFIRMED** (measured ordering) — in the background closure (`handler.rs:161-178`), `run_preview` returns and drops `client: WorkerClient` (owning the `Child` handle, `crates/client/src/lib.rs:50`, `Drop` :282-289); only afterwards does `handler.rs:174` run `pid.store(0, Ordering::Relaxed);`. Meanwhile `stop_preview` (`handler.rs:233-242`) and `unload` (`handler.rs:188-198`) do `OpenProcess(PROCESS_TERMINATE, 0, pid)` + `TerminateProcess`.
- Mitigations already in place that make the PID path redundant: `JobGuard` uses `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`job.rs:23-27`) and terminates on Drop (`job.rs:61-68`), and is created before work starts.
- Size: S · Model effort: entry-level OK
- Depends on: nothing; land before L5 (same file `handler.rs`).
- Manager sign-off: not required.

## Root cause
Two kill mechanisms exist (job + PID), and the bookkeeping for the redundant one lags the resource it describes: the PID slot can describe an already-reaped process ID that Windows may hand to an unrelated process.

## Fix (minimal — preferred)
- Delete the PID kill path entirely: `handler.rs:188-198` (unload branch) and `handler.rs:233-242` (stop_preview PID branch), plus the `worker_pid` field if it becomes unused. The job's kill-on-close already terminates the right process; selection-change and unload paths both terminate the job.
- Alternative (if the fixer finds a live caller needing the PID for logging only): keep the field for telemetry but clear it (`pid.store(0)`) as the *first* statement after `run_preview` finishes its work, before `client` leaves scope. Rejected as primary because it preserves a second kill mechanism for no benefit.

## Acceptance test
- Fails-before test is hard to build for a narrow recycling race without OS fiddling; use the structural guarantee instead: test `stop_preview_is_safe_without_worker_pid` (new `#[cfg(test)]` in `handler.rs`, which currently has no tests): construct the handler state as after `run_preview` completion (pid=0, no job), call `stop_preview`, assert no `OpenProcess`/`TerminateProcess` occurs — observable by the fact it returns cleanly and does not touch `ffi::OpenProcess` (hide behind a test seam if needed).
- Stronger automated proof: the Windows-native end-to-end test specced in L6 (CoCreateInstance + DoPreview + Unload loop) asserts no worker process or temp file remains after unload; it exercises the job path directly.
- Manual on this PC: preview trades.parquet, press F/arrows rapidly for 30 s (dozens of kill/replace cycles), and confirm no wrong-process kills: the session stays intact and no unrelated process dies (hard to assert formally — mark as smoke).

## Risk / blast radius
- Small but in the hottest cancel path. Risk: if any path relied on PID-kill while the job was absent, stops stop working. Grep first — at the pinned SHA, job creation precedes every work path (verified), so the seam is safe.
- L5 will extend `handler.rs` (site/surface code); land L3 first to keep both diffs small.
