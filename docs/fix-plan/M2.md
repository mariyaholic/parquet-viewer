# parquet-viewer M2 — Worker kills leave copies of user Parquet data in `%TEMP%`

- Severity: medium
- Pinned SHA verified: `e815e646e6d261291417730ac79345da81e7f6f9`
- Status: **CONFIRMED** — `crates/worker/src/spool.rs:113-116`: cleanup exists only in `Drop for SpoolFile`; `spool.rs:44-50` opens the spool with plain `read(true).write(true).create_new(true)` (no `custom_flags`/`share_mode` anywhere). - ⚠ **Needs an explicit Manager sign-off line before the fixer starts** (marked in the review as requiring decision — the sweep deletes stale temp files en masse).
- Size: S · Model effort: entry-level executor OK

## Root cause
Terminating a process runs no Rust destructors, so `Drop`-based cleanup never runs for the most common exit path. On Windows nothing else deletes the spool: the file is created with `create_new` and no delete-on-close flag, and no sweep ever runs. Arrowing through a folder of Parquet files leaks up to 64 MiB of user data per selection change, indefinitely.

## Fix (minimal)
1. `crates/worker/src/spool.rs`, `SpoolFile::new` (lines 26-67): in a `#[cfg(windows)]` branch parallel to the existing `#[cfg(unix)]` branch (lines 46-50), add `.custom_flags(FILE_FLAG_DELETE_ON_CLOSE /* 0x0400_0000 */)` and `.share_mode(FILE_SHARE_READ | FILE_SHARE_DELETE)` via `std::os::windows::fs::OpenOptionsExt`. The kernel deletes the file when the killed process's last handle closes — no destructor needed. `take_file` (`spool.rs:96-105`) handing the `File` out still works: deletion happens at last-handle close.
2. Belt-and-braces sweep at worker startup (`crates/worker/src/main.rs` before serving): delete `%TEMP%\parquet-preview-*.tmp` older than 1 hour. Only files matching the prefix and age threshold; ignore errors.
3. Keep the `Drop`-based `remove_file` for Unix and graceful exits.

## Acceptance test
- Unit (portable): test the sweep helper — create fake `parquet-preview-*.tmp` files with old and new mtimes and assert only the old ones are removed (mktime manipulation via `filetime`-style API or `std::fs::set_modified`… on Windows use `filetime` crate already in tree or `SetFileTime` in the worker; the fixer should check which dependency is available and use that rather than adding one).
- Fails-before/passes-after (Windows): a `#[cfg(windows)]` test in `spool.rs` that creates a `SpoolFile`, obtains the path, terminates…, too heavy for a unit test — instead assert via a spawned worker: reuse the real-binary scaffolding in `crates/worker/tests/client.rs` (already has 3 process tests). Add a test that opens a stream, hard-kills the client mid-transfer, waits for the process to exit, and asserts the `.tmp` is gone. Before the fix: file persists → test fails; after: kernel delete-on-close → passes. On Linux this guard stays the existing `Drop` path.
- Wait—the kill test in `client.rs:68-83` is `#[cfg(target_os = "linux")]` today (L6 covers making it cross-platform; this M2 test should be written to run on Windows from the start, using `OpenProcess`+`WaitForSingleObject(0)`).
- Manual on this PC (primary acceptance, since it is real kill semantics): preview a large fixture, change selection within ~100 ms, repeat 20 times; then check `%TEMP%` — `Get-ChildItem $env:TEMP parquet-preview-*.tmp` must be empty afterwards. Also: preview a decompression-heavy file that trips the 512 MiB job kill and re-check.

## Risk / blast radius
- Small and local to `worker/src/spool.rs` + `main.rs`. Risk: if `share_mode` is set wrong, the handler-side reader (`take_file` path) could fail to open the file concurrently — the existing `append_and_read_back` test (`spool.rs:124-138`) covers normal read/write and must still pass.
- Existing stale-file sweep must not delete files belonging to *live* workers: prefix + 1-hour age guard handles it; workers run shorter than that per file under normal use.
