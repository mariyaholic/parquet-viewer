# parquet-viewer M1 — Explorer preview path snapshots the whole file into RAM on the host thread, with a hard 64 MiB ceiling

- Severity: medium
- Pinned SHA verified: `e815e646e6d261291417730ac79345da81e7f6f9`
- Status: **CONFIRMED** — `crates/windows/src/copy_stream.rs:6` `MAX_SNAPSHOT_BYTES = 64 MiB`; snapshot runs synchronously inside `do_preview` (`handler.rs:137-138`) while the `state` mutex is held (`com.rs:266-271`); the worker itself accepts `max_file_bytes: 16 GiB` (`crates/core/src/limits.rs:58`). The 64 MiB cap is documented only in `STATUS.md:3` and `docs/TESTING.md:108`, not in README "Known limitations" (`README.md:137-149`).
- Two failure modes: (1) every Parquet file over 64 MiB is refused with an error although Parquet preview needs only footer + a few pages; (2) for files under 64 MiB the synchronous read blocks prevhost's STA — slow streams (SMB, OneDrive placeholders) freeze the pane and cancellation cannot interrupt since `stop_preview` runs on the same thread.
- Size: L (full fix) / S (disclosure-only fallback) · Model effort: strongest available for the marshalling fix; entry-level for the fallback
- Depends on: H1 first (same file `handler.rs`; avoids rebase conflicts).
- Manager sign-off: not required, but this is a **scope decision** — fix now or disclose now (see Open questions).

## Root cause
A round-2 "fix" (Terra `e85a636`) replaced the original cross-apartment raw-pointer hazard with an in-memory snapshot taken on the host COM thread. That removed a crash risk but reintroduced two older problems the architecture document explicitly forbids: RAM-populating the whole stream, and a size ceiling (`docs/ARCHITECTURE.md:22` calls for "bounded IPC or private bounded temporary spool").

## Fix (primary: marshal, then stream)
1. Keep the current architecture: `IPreviewHandler::Initialize` receives an `IStream`; do **not** copy it into RAM.
2. In `do_preview` (`crates/windows/src/handler.rs:113-179`), marshal the stream for the background thread with `CoMarshalInterThreadInterfaceInStream` (new FFI in `crates/windows/src/ffi.rs`; that file has no marshalling bindings yet). The thread that later runs the work releases it via `CoGetInterfaceAndReleaseStream` after `CoInitializeEx` on the worker-side thread created for `run_preview`.
3. On the background thread, pump 64 KiB chunks straight into `WorkerClient::open_stream` (already takes `&mut dyn Read`, `crates/client/src/lib.rs:140-173` — reusable unchanged), checking the `cancel` flag between chunks so `stop_preview` can interrupt.
4. Delete `MAX_SNAPSHOT_BYTES` and `snapshot` in `copy_stream.rs` (and its 2 tests, `copy_stream.rs:30-47`), or repurpose the file for the chunk-pump wrapper.
5. Cancel plumbing: `open_stream` itself has no cancel hook; put the check in a small `Read` wrapper owned by the preview loop rather than changing the protocol.

### Alternative (disclosure-only), if the Manager defers
- One paragraph in `README.md:137-149`: "Explorer preview is limited to files ≤ 64 MiB; larger files will be refused." Zero code risk; no Win32/COM work. This was rejected as the primary path because the cap defeats the product's core use for real-world Parquet files, and the ARCHITECTURE doc already promises the bounded-stream design.

## Acceptance test
- Unit (runs on Windows CI or this PC): `tests:` a memory-stream-backed `IStream`… heavy; pragmatic substitute: an integration-style test that runs `do_preview`'s pump function (extracted, platform-neutral where possible) over a 200 MiB in-memory parquet fixture through the fake worker protocol, asserting it completes and cancels mid-stream when `cancel` is set.
- Behaviour test that fails before / passes after: with a ≥ 100 MiB file, `do_preview` before the fix returns "stream size … exceeds snapshot limit"; after, it renders footer + sample rows. Automated assertion belongs in the new pump unit test (cancel between chunks). Wine cannot run prevhost/COM here; the PC check below is mandatory.
- Manual on this PC: preview a 200 MiB Parquet in Explorer; then a ~60 MiB file on an SMB path while changing selection mid-load — the pane must stay responsive and the new file must preview immediately.

## Risk / blast radius
- Largest change in this repo: touches `handler.rs`, `ffi.rs`, possibly deletes `copy_stream.rs`. New COM API usage is the main risk — a refcount/marshal mistake can leak or crash prevhost. Keep the existing worker job/kill machinery untouched (M2 lands separately in `worker/src/spool.rs`, no conflict).
- H1 must land first (same file), L5 also touches `handler.rs` later.
- If COM marshalling proves flaky in testing, fall back to the disclosure path rather than shipping half a fix.
